# Cairn Next 0.2.0-rc.2 사용 설명서

이 문서는 밝은 UI를 적용한 0.2.0-rc.2의 사용·복구·로컬 빌드 절차입니다. 공개 브랜치는 소스만 제공하며 설치기·포장 앱·QA 프로필은 포함하지 않습니다. 과거 Windows 로컬 시험과 미검증 범위는 [RC1 검증 기록](release-validation.md)과 [출시 준비 상태](release-readiness.md)를 확인하세요. 명령 예시를 기재한 사실은 그 명령을 실행해 검증했다는 뜻이 아닙니다.

기존 Cairn은 저장소 루트의 별도 앱입니다. Cairn Next와 기존 Cairn의 협업 프로토콜·내부 데이터는 호환되지 않으며 자동 마이그레이션하지 않습니다. 소스 실행은 저장소 루트에서 `cd cairn-next` 후 [README의 절차](../README.md#run-from-source)를 따릅니다.

## 로컬 프로젝트 열기

1. 첫 실행에서 표시 이름과 화면 언어를 정합니다. 표시 이름은 팀의 활동·커서에 표시되며 외부 계정 인증을 의미하지 않습니다.
2. **프로젝트 → 폴더 열기**에서 일반 로컬 폴더를 선택합니다. 중요한 기존 작업은 먼저 별도 백업을 마련하는 것이 좋습니다.
3. **공유에서 제외된 항목**을 확인합니다. 제외된 파일은 삭제하지 않으며 원래 위치에 남습니다.
4. **파일**에서 항목을 선택합니다. 지원 텍스트는 편집기로 열리고, 바이너리는 형식·크기 안내나 지원되는 미리보기를 표시합니다. Office 문서나 영상을 공동 텍스트 편집할 수는 없습니다.
5. 파일 생성·이름 변경·이동은 프로젝트 내부의 상대 경로를 사용합니다. 삭제 확인에는 대상과 영향을 받는 하위 파일이 표시됩니다.

로컬 폴더는 앱 내부의 비공개 loopback 팀 연결로 편집합니다. 원래 폴더를 감시·반영하는 구성요소는 하나이며, 앱 편집용 내부 사본과 실제 프로젝트 폴더는 분리됩니다. **폴더에서 보기**는 선택한 실제 프로젝트 폴더를 대상으로 합니다.

최근 목록의 **목록에서 제거**는 목록 항목만 지웁니다. 파일·기록·내부 DB를 삭제하지 않습니다. 폴더를 이동했다면 **폴더 다시 찾기**로 실제 위치를 지정합니다. 프로젝트 식별자가 맞지 않는 폴더를 기존 프로젝트인 것처럼 연결하지 않습니다.

구버전 `.cairn`, `.cairn-next-client`, 또는 0.1.x `server.sqlite`/`client.sqlite`가 있는 폴더는 직접 업그레이드하지 않습니다. 원본과 숨김 기록을 보존하고 일반 파일만 새 폴더에 복사한 뒤 여세요. 이는 파일 가져오기이며 과거 활동·체크포인트 기록의 변환은 아닙니다.

## 팀 만들기와 참가

1. 생성자는 로컬 프로젝트를 열고 **팀 → 팀 만들기**를 선택합니다. 같은 프로젝트의 연결이 LAN에 노출되고 근처 팀 검색 정보가 광고됩니다.
2. 팀원에게 필요한 **편집자** 또는 **열람자** 권한을 선택해 초대를 복사합니다. 기본 초대 유효기간은 24시간입니다. 초대에는 접근 토큰이 있으므로 비밀번호처럼 다룹니다.
3. 참가자는 **팀 참가**에서 초대를 붙여넣고 빈 로컬 작업 폴더를 선택합니다. 이미 해당 프로젝트와 일치하는 사본은 재연결 대상으로 사용할 수 있습니다. 관계없는 파일이 있는 폴더에 덮어쓰지 않습니다.
4. 초기 다운로드 뒤 내용 검증과 이후 변경 적용까지 완료되면 편집이 준비됩니다. 다운로드가 끊겼다면 취소·재시도할 수 있으며, 불완전한 파일을 확인 완료로 표시하지 않습니다.
5. 생성자와 참가자는 초대의 인증서 fingerprint를 신뢰하는 별도 경로로 비교할 수 있습니다. 근처 팀 목록은 연결 후보를 찾는 기능이며 인증을 대신하지 않습니다.

열람자는 공유된 내용과 기록을 읽을 수 있지만 편집·복원 같은 변경을 실행할 수 없습니다. 생성자는 **팀**에서 멤버의 접근 권한을 폐기할 수 있습니다. 이미 팀원이 받은 파일 사본을 원격에서 지우는 기능은 아닙니다.

초대가 만료되면 생성자에게 **기존 멤버용 갱신 초대**를 받아 같은 작업 사본으로 다시 연결하세요. 갱신 초대는 기존 멤버 식별자를 유지하며 24시간 유효합니다. 기존 작업 사본이나 전달 대기 편집을 삭제하고 처음부터 참가할 필요는 없습니다. 폐기된 권한은 소유자의 명시적인 새 허용 없이 되살아나지 않습니다.

근처 팀이 보이지 않으면 유효한 초대의 직접 WSS 주소를 사용하세요. IP 주소가 바뀌어도 인증서와 팀 식별자를 임의로 바꾸거나 TLS 검증을 끄지 않습니다. 같은 네트워크인지, 생성자의 앱이 열려 있는지, 주소·포트와 OS 방화벽 허용이 맞는지 확인합니다. 앱은 방화벽이나 공유기를 자동 설정하지 않습니다. 팀원에게 `127.0.0.1`/`localhost` 주소를 전달하면 안 됩니다.

VPN·게스트 Wi-Fi·장치 격리 정책 때문에 검색이나 직접 연결이 막힐 수 있습니다. 인터넷 중계, NAT 통과, 중앙 저장소 또는 항상 켜진 호스팅 서비스는 포함하지 않습니다.

## 저장 상태와 종료

| 화면 상태                       | 의미                                                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 아직 이 창에만 있는 입력        | 영속 보관 전 입력입니다. 경고를 해소하거나 별도로 보관하세요.                                        |
| 내 기기에 보관됨                | 이 기기의 로컬 저장소에 기록되었습니다. 팀 전달 완료와는 다릅니다.                                   |
| 팀에 전달 대기 중               | 로컬 변경이 저장되어 있으나 기준 프로젝트에 아직 확인되지 않았습니다.                                |
| 팀에 보관됨                     | 생성자 쪽 프로젝트 저장소가 해당 변경을 영속 기록했습니다.                                           |
| 폴더에 반영 대기 중 / 확인 필요 | DB의 최신 내용과 실제 일반 파일의 상태가 아직 다를 수 있습니다.                                      |
| 폴더에 반영됨                   | 현재 장치의 일반 파일 반영이 완료되었습니다.                                                         |
| 현재 연결된 팀원 확인 완료      | 그 시점의 연결된 참가자들이 최신 내용과 파일 반영을 확인했습니다. 오프라인 팀원은 포함하지 않습니다. |

작업을 마칠 때 대기·거부·충돌·폴더 반영 경고를 먼저 확인합니다. 정상 종료하면 이 앱이 소유한 연결과 호스팅이 중지됩니다. 이 버전은 트레이로 숨겨 계속 서비스하거나 OS 시작 때 자동으로 서버를 실행하지 않습니다. 생성자의 앱 종료·PC 절전·전원 종료 동안 팀원은 기준 프로젝트에 새 변경을 보낼 수 없습니다.

오프라인에서도 이미 열린 텍스트의 로컬 편집은 보관될 수 있지만 파일 구조 변경, 공유 복구 작업 등은 연결이 필요합니다. 재연결 후 기준 상태가 바뀌었다면 오래된 편집을 무조건 덮어쓰지 않고 충돌로 보존합니다. 저장되지 않은 입력 경고가 있다면 강제 종료하지 말고 해당 입력을 먼저 보관하세요.

설정의 **PC 서버 — Coming Soon**은 향후 기능 안내입니다. 현재 버전의 설치 프로그램이나 UI에는 독립·상주 서버의 제품 사용 흐름이 없습니다.

## 외부 편집기와 작업 알림

프로젝트 폴더는 일반 폴더이므로 IDE·텍스트 편집기·기타 도구에서 열 수 있습니다. 외부 변경 감시를 켜면 저장된 파일을 검사합니다. 앱은 다른 프로그램의 **아직 저장하지 않은 버퍼**를 읽거나 그 프로그램에 저장을 강요하지 않습니다.

1. 외부 편집 전에 Cairn과 실제 폴더가 최신인지 확인합니다.
2. 가능하면 해당 파일의 **외부 편집 작업 알림**을 시작하고 무엇을 할지 설명합니다. 이 claim은 기준 내용을 기록하고 해당 작성자 사본의 원격 파일 반영을 잠시 보류합니다.
3. 외부 도구에서 편집한 뒤 저장합니다.
4. Cairn에서 알림을 완료합니다. 완료·취소·만료 시 실제 파일 상태를 다시 확인하며, 내용이 오래된 기준이면 충돌로 남깁니다.

기본 claim은 협업 알림이며 OS 파일 잠금이 아닙니다. 엄격한 claim을 사용하는 프로젝트에서는 다른 작성자의 서버 변경이 거절될 수 있습니다. 자신의 claim은 갱신·완료·취소할 수 있고, 소유자는 오래된 claim을 취소할 수 있습니다. 기본 유효기간은 30분이며 갱신 없이 무제한 유지되지 않습니다.

기준이 최신인 외부 텍스트 저장은 최소 텍스트 차이로 기존 공동 편집 상태에 반영합니다. 기준이 오래되었거나 알 수 없거나 파일 형식이 달라졌다면 기존 버전과 새 내용을 보존합니다. 바이너리 저장은 내용 해시 기준으로 검사하며 텍스트처럼 자동 병합하지 않습니다.

활동의 **AI로 선언됨**은 사용자가 명시한 출처입니다. 파일 이름·프로세스 이름으로 AI 사용을 추측하거나 AI 서비스의 인증된 활동이라고 표시하지 않습니다. Cairn 자체가 프로젝트 내용을 AI 서비스로 전송하는 기능은 없습니다.

## 활동, 충돌, 체크포인트, 삭제된 파일

**활동**에서는 경로·작성자·출처로 검색하고 파일 또는 세션 단위로 묶어 볼 수 있습니다. 기록을 열면 이전/이후 내용과 텍스트 차이를 비교할 수 있습니다. 큰 차이나 바이너리는 제한된 미리보기를 사용합니다. 세션 묶음은 탐색 기능이며 세션 전체 자동 롤백 기능은 아닙니다.

**충돌**에서는 내 버전·팀 버전·가능한 기준 버전을 비교합니다. 내 버전 유지, 팀 버전 유지, 둘 다 별도 파일로 보관 중에서 선택할 수 있습니다. 지원 텍스트는 수동 병합도 가능합니다. 바이너리는 자동 텍스트 병합하지 않습니다. 비교한 이후 다른 변경이 들어오면 새 상태를 확인해야 합니다.

**체크포인트**는 이름을 붙인 프로젝트 상태입니다. 비교 후 선택 파일 또는 프로젝트를 복원할 수 있습니다. 복원 직전 상태를 보호용 체크포인트로 먼저 보관하며 복원 자체도 새 변경으로 기록합니다. 오래된 클라이언트 편집은 복원된 문서를 몰래 되살리거나 덮어쓰지 않고 별도로 보존합니다. 복원은 DB 파일을 과거 사본으로 교체하는 작업이 아닙니다.

**삭제된 파일**에서 복원하거나 선택 항목을 영구적으로 목록에서 비울 수 있습니다. 기본 보관기간은 30일이며 설정 가능한 범위는 1–3,650일입니다. 기한이 지난 항목은 호스트가 실행 중일 때 정리됩니다. 비우기나 보관기간 단축은 삭제된 항목의 복구 목록을 대상으로 하며 **별도 체크포인트를 삭제하지 않습니다**. 불변 blob·작업 기록·다른 참가자의 사본까지 안전하게 지우는 기능은 아니므로 “디스크 흔적 완전 삭제”로 해석하지 마세요.

체크포인트는 최대 64개입니다. claim·충돌·삭제 기록과 전체 복구 메타데이터에도 한도가 있습니다. 한도 오류가 나면 필요한 자료를 별도로 보관하고 화면에서 명시적으로 불필요한 기록을 정리하세요. 내부 DB 행을 직접 삭제하지 않습니다.

## 파일 형식과 제외 규칙

| 대상                         | 지원 범위                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| 텍스트 공동 편집             | UTF-8, NUL 등 바이너리 제어문자 없음, 일관된 LF/CRLF, 최대 1 MiB                           |
| 바이너리 전송                | 이미지·Office·PDF·오디오·영상·기타 바이트 파일, 최대 16 MiB                                |
| 큰 텍스트·특수 인코딩        | 1 MiB 초과 텍스트, BOM, 비 UTF-8, 혼합 줄바꿈은 최대 16 MiB까지 바이너리 처리              |
| 현재 프로젝트 내용           | 최대 256 MiB, 디렉터리를 포함해 최대 5,000개 항목                                          |
| 공동 편집 내부 상태·업데이트 | 각각 최대 4 MiB                                                                            |
| 경로                         | `/`로 구분한 NFC Unicode 상대 경로, 전체 최대 1,024 UTF-8 바이트, 부분 이름 최대 255바이트 |

절대 경로, `..`, 역슬래시, 예약 이름(`CON`, `NUL` 등), 끝의 점·공백, 대소문자 충돌과 symlink/junction은 허용하지 않습니다. 지원되지 않는 파일은 기존 디스크에 보존합니다. 디렉터리 삭제는 외부 도구가 만든 미지의 자식까지 재귀 삭제하지 않습니다.

한 번의 이동·삭제·복원 등에 필요한 변경 기록과 동기화 목록에는 별도의 20 MiB 한도가 있습니다. 매우 긴 경로가 많은 대규모 작업이 이를 넘으면 변경을 저장하기 전에 전체 작업을 거절하고 이전 상태를 유지합니다. 파일이나 하위 폴더를 나누어 작업하세요. 이력 전달도 한 번에 이 한도 안에서 처리하며 남은 순서를 이어서 확인합니다.

기본 제외 예:

- 비밀정보: `.env`, `.env.*`, `.env-*`, `.npmrc`, `.pypirc`, `.netrc`, `credentials`, `credentials.json`, `id_rsa`/`id_ed25519` 등 키 파일, `.pem`/`.key`/`.pfx`/`.p12`/`.jks`/`.keystore`.
- 내부 기록·버전 관리: `.cairn*`, `.git`, `.svn`, `.hg`.
- 의존성·빌드·캐시: `node_modules`, `bower_components`, `dist`, `build`, `out`, `target`, `.next`, `.nuxt`, `.output`, `.cache`, `.parcel-cache`, `.turbo`, `.svelte-kit`, `.vercel`, `.netlify`, `coverage`.
- 개발환경·개인정보: `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.venv`, `venv`, `.gradle`, `.ssh`, `.aws`, `.azure`, `.gnupg`, `.gcloud`.
- 임시·OS 파일: `tmp`, `temp`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `.tmp`/`.temp`/`.swp`/`.swo`, `~$`·`.#`·백업 이름.

프로젝트 `.gitignore`와 설정의 추가 패턴도 적용됩니다. 기본 제외 항목은 `!` 예외 규칙으로 공유할 수 없습니다. 새 제외 규칙은 관련 파일을 공유 대상에서 빼되 원래 디스크 파일을 삭제하지 않습니다. 과거에 이미 다른 사람에게 전달된 파일 사본까지 회수하지는 않습니다.

비밀 문자열이 일반 소스 파일에 포함되면 이름 규칙만으로 찾지 못할 수 있습니다. 팀 공유·ZIP·GitHub 업로드 전에 실제 내용을 검토하세요. 네트워크 드라이브·클라우드 동기화 폴더의 동시 쓰기와 SQLite/하드링크 동작은 이 후보의 검증 범위로 간주하지 않습니다.

## 저장 위치와 백업

| 데이터                                              | 위치                                                                                           |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 생성자의 일반 파일                                  | 처음 연 실제 프로젝트 폴더                                                                     |
| 참가자의 일반 파일                                  | 참가할 때 선택한 작업 사본 폴더                                                                |
| 각 프로젝트의 내용·상태·기록·체크포인트·충돌·outbox | 해당 작업 폴더의 `.cairn-next/project.sqlite` 및 SQLite 관련 파일                              |
| 호스트 팀 ID·인증서·개인 키·초대 해시               | 생성자 프로젝트의 `.cairn-next/team.sqlite`                                                    |
| 프로세스 소유권 기록                                | `.cairn-next/ownership.sqlite`                                                                 |
| 호스트 파일 반영의 보호 사본·의도 기록              | `.cairn-next/recovery/`                                                                        |
| 참가자 파일 반영의 보호 사본                        | `.cairn-next/replica-recovery/`                                                                |
| 생성자의 내부 편집 사본                             | 앱 사용자 데이터의 `owner-workcopies/<projectId>/`; 내부에도 `.cairn-next/project.sqlite` 사용 |
| 최근 프로젝트·언어·선택 상태·팀 포트·GitHub 대상    | 앱 사용자 데이터의 `profile.json`; 토큰은 넣지 않음                                            |
| OS 암호화된 초대·GitHub 토큰                        | 앱 사용자 데이터의 `secrets.encrypted`                                                         |
| ZIP 게시가 실패했을 때 남는 자료                    | 선택한 출력 폴더의 `.cairn-export-<고유값>.tmp`; 오류가 복구 경로를 포함할 수 있음             |

기본 앱 사용자 데이터는 Windows의 `%APPDATA%/<앱 이름>/`, macOS의 `~/Library/Application Support/<앱 이름>/` 형태입니다. 실제 기본 폴더명은 이번 격리 프로필 시험에서 확인하지 않았습니다. 시험에서는 `CAIRN_USER_DATA`로 별도 프로필을 지정할 수 있으며 그 경로가 우선합니다. `profile.json`·`secrets.encrypted`·`owner-workcopies`가 있는 해당 앱 프로필을 보존하세요. 진단 정보 복사는 이 디렉터리의 전체 경로를 출력하지 않습니다.

백업은 다음 순서로 합니다.

1. 모든 관련 앱에서 입력이 로컬에 보관되었는지 확인합니다. 연결 대기 변경이 있다면 해당 참가자의 작업 사본도 백업 대상입니다.
2. 생성자와 참가자 앱을 정상 종료합니다.
3. 일반 파일뿐 아니라 `.cairn-next` 전체를 포함해 다른 위치에 폴더 사본을 만듭니다. 생성자의 내부 편집 사본과 필요한 앱 프로필도 별도로 보관합니다.
4. 원본을 유지한 채 백업 파일 목록·크기·해시를 확인합니다. 실행 중 DB 본체만 가져오거나 `-wal`/`-shm`을 지우지 않습니다.

호스트의 `team.sqlite`와 앱 프로필에는 민감한 접근 자료가 있습니다. 백업은 비공개 위치에 보관하고 소스 저장소·일반 ZIP 내보내기에 섞지 않습니다. OS 보안 저장소로 암호화된 토큰은 다른 OS 계정이나 PC에서 복호화되지 않을 수 있으며 다시 입력할 수 있어야 합니다.

파일 잠금·권한·공간 부족 때문에 폴더 반영이 멈추면 일반 파일과 DB 모두 보존한 채 원인을 해결하고 **파일 반영 재시도**를 사용합니다. 오류를 없애려고 내부 폴더나 충돌 기록을 지우지 마세요. 어떤 버전이 필요한지 불명확하면 먼저 전체 사본을 확보합니다.

## ZIP과 GitHub 내보내기

**ZIP**은 선택 시점의 일관된 프로젝트 내용을 새 파일로 저장합니다. 기존 출력 파일을 덮어쓰지 않으며 각 파일의 내용 해시와 경로를 재검증합니다. 디렉터리와 원본 바이너리를 포함하고 `.cairn-snapshot-manifest.json`에 파일별 SHA-256·크기·시점 정보를 기록합니다. 앱 DB, 공동 편집 내부 상태, 활동 이력, 토큰, 체크포인트는 넣지 않습니다. 따라서 ZIP은 일반 파일 전달용이며 전체 앱 기록 백업을 대신하지 않습니다.

**GitHub** 절차:

1. 설정에 저장소 소유자·이름·기준 브랜치를 지정하고 해당 저장소에 필요한 권한을 가진 토큰을 입력합니다. 내용 읽기, 게시 시 내용 쓰기와 PR 생성 권한이 필요합니다. 조직 정책에 따라 별도 승인도 필요할 수 있습니다.
2. **미리보기**에서 원격 기준과 다른 파일·텍스트 차이를 확인합니다. 이 단계는 GitHub 읽기 요청만 실행합니다.
3. 보낼 파일을 명시적으로 선택합니다. 원격에만 있는 파일은 삭제 후보로 나타날 수 있지만 기본 선택되지 않습니다. 무관한 원격 파일을 삭제하지 않도록 대상 목록을 확인합니다.
4. PR 제목·설명을 확인하고 게시를 명시적으로 실행합니다. 게시 전에 기준 브랜치와 선택 파일 해시를 다시 검사합니다.
5. 새 고유 브랜치에 변경을 만들고 PR을 생성합니다. 기존 브랜치를 강제로 수정하거나 병합하지 않습니다.

기준 브랜치가 움직였다면 새 미리보기를 만들고 다시 선택하세요. 큰 텍스트·바이너리의 차이는 제한적으로 표시될 수 있지만 내용 해시와 전송 바이트는 검사합니다. 업로드 후 PR 생성이 실패하면 새 브랜치·커밋이 복구를 위해 남을 수 있습니다. 무작정 재시도하기 전에 안내된 브랜치를 확인합니다. 실패 정리 과정에서 기존 저장소 상태를 삭제하지 않습니다.

프로덕션 대상은 `https://api.github.com`입니다. 임의 API 주소·GitHub Enterprise 서버 설정은 UI에 제공하지 않습니다. 자동 시험은 명시적으로 허용된 loopback 모의 서버만 사용하며 실제 토큰·원격 PR을 사용하지 않습니다.

## 설치와 제거

이 브랜치에는 다운로드할 설치기가 없습니다. 아래 절차는 소스에서 직접 만든 로컬 시험 산출물을 대상으로 합니다. 저장소 루트에서 `cd cairn-next`로 이동하고 Node 24.x(24.19.0 이상)와 pnpm 11.25.0을 준비한 뒤 빌드합니다.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm start
```

### Windows

이미 포장된 앱의 실행에는 Node.js·pnpm이 필요하지 않습니다. 직접 빌드한 뒤 다음 명령으로 로컬 실행 폴더 또는 설치기를 만들 수 있습니다. 산출물은 `cairn-next/release/`에 생성되며 원격 게시하지 않습니다.

```sh
pnpm pack:win --publish never
pnpm dist:win --publish never
```

설치 프로그램은 현재 사용자 범위이며 설치 위치를 선택할 수 있습니다. `win-unpacked`를 사용할 때는 exe와 리소스가 든 폴더 전체를 보존합니다. 현재 후보는 OS 배포 서명을 하지 않습니다. [출시 준비 상태](release-readiness.md)의 파일명·해시는 과거 RC1 기록이며 새로 만든 RC2 산출물의 값으로 사용하지 않습니다.

검증용 설치는 기존 프로그램·개인 프로젝트와 분리된 위치에서 합니다.

1. 새 시험용 설치 폴더, 프로젝트 폴더, 앱 프로필 폴더를 마련합니다. 평소 사용하던 프로젝트를 시험 대상으로 사용하지 않습니다.
2. 후보 설치 프로그램을 실행하고 새 설치 폴더를 선택합니다.
3. PowerShell에서 시험용 앱 프로필을 지정하고 설치된 실행 파일을 직접 실행합니다. 경로는 방금 선택한 위치로 바꿉니다.

   ```powershell
   $env:CAIRN_USER_DATA = Join-Path $env:TEMP ('cairn-rc-profile-' + [guid]::NewGuid())
   & (Join-Path $env:LOCALAPPDATA 'Cairn-RC-Trial\Cairn Next.exe')
   ```

4. 시험 프로젝트를 열고 텍스트·바이너리·체크포인트를 만든 뒤 정상 종료합니다. 일반 파일과 `.cairn-next`의 존재를 확인합니다.
5. 같은 설치 위치에서 재실행해 최근 목록과 프로젝트 내용이 이어지는지 확인합니다.
6. Windows 설정의 설치된 앱 또는 설치 폴더의 제거 프로그램으로 제거합니다. 제거 대상은 설치된 앱입니다. 설정상 앱 사용자 데이터 자동 삭제는 꺼져 있으며, 사용자가 별도로 선택한 프로젝트 폴더를 삭제하지 않습니다.
7. 설치 전후의 시험 프로젝트·숨김 기록·앱 프로필 보존을 직접 비교합니다. “설정이 보존하도록 되어 있음”과 “해당 설치 프로그램으로 실제 검증함”은 별개이므로 결과를 기록합니다.

목록에서 프로젝트 제거, 앱 제거, GitHub 토큰 지우기, 삭제된 파일 비우기는 각각 다른 범위입니다. 어느 하나가 모든 프로젝트 기록이나 OS 백업까지 지우는 것으로 해석하지 마세요. 앱을 다시 설치하더라도 기록을 지우려는 목적으로 프로젝트 내부 폴더를 삭제하지 않습니다.

### macOS 빌드와 시험 — 미검증·미서명

기록된 Windows 시험에서는 macOS 앱을 빌드·실행·설치하거나 macOS IME·Keychain·실제 LAN을 검증하지 않았습니다. 아래는 **실제 Mac에서 수행해야 할 절차**입니다. Developer ID 서명과 Apple 공증은 수행하지 않습니다. 바이너리 배포나 Gatekeeper 통과를 주장하지 않습니다.

1. 별도 검증용 checkout을 실제 Mac에 준비합니다. 기존 사용자 프로젝트·프로필과 분리하고 Node 24.x, pnpm 11.25.0, 해당 Mac의 Xcode Command Line Tools를 준비합니다. Windows의 `node_modules`와 Electron 바이너리를 복사해 재사용하지 않습니다.
2. 저장소 루트에서 `cd cairn-next`로 이동한 뒤 다음 명령을 실행합니다.

   ```sh
   node --version
   pnpm --version
   pnpm install --frozen-lockfile
   pnpm verify
   pnpm runtime:check
   pnpm test:desktop
   node scripts/generate-notices.cjs
   node scripts/generate-notices.cjs --check
   ```

3. Apple Silicon Mac에서 다음 명령으로 업로드 없이 미서명 ARM64 DMG를 만듭니다. Intel Mac에서는 `--arm64`를 `--x64`로 바꿉니다. 각각의 결과는 해당 CPU 환경에서 따로 검증합니다.

   ```sh
   CSC_IDENTITY_AUTO_DISCOVERY=false pnpm exec electron-builder \
     --mac dmg --arm64 --publish never \
     -c.mac.identity=null -c.mac.notarize=false -c.mac.hardenedRuntime=false
   ```

4. `release/`의 DMG와 생성된 `.app` 경로를 기록하고 SHA-256을 계산합니다. 실제 생성된 파일명을 사용하세요.

   ```sh
   shasum -a 256 release/*.dmg
   codesign -dv --verbose=4 'release/mac-arm64/Cairn Next.app'
   spctl --assess --type execute --verbose=4 'release/mac-arm64/Cairn Next.app'
   ```

   미서명·미공증 후보의 서명 검사나 Gatekeeper 평가는 거부될 수 있습니다. 이를 통과로 기록하거나 보안 설정을 전역으로 해제하지 않습니다. 개발 검증 진행 여부는 검사 결과와 출처를 확인한 사용자가 결정해야 합니다.

5. DMG를 열어 시험용 위치로 앱을 복사합니다. 격리 프로필로 내부 실행 파일을 실행합니다. 아래 경로는 생성된 실제 앱 위치로 바꿉니다.

   ```sh
   CAIRN_USER_DATA="$(mktemp -d /tmp/cairn-rc-profile.XXXXXX)" \
     'release/mac-arm64/Cairn Next.app/Contents/MacOS/Cairn Next'
   ```

6. 새 시험 폴더에서 로컬 열기·복수 파일 편집·바이너리 보존·이름 변경·하위 폴더 이동·삭제·복원·체크포인트 복원을 수행합니다. LF/CRLF와 한국어·번체 중국어 IME 조합 입력, 본인 Undo/Redo, 앱 종료·재시작 후 내용과 해시를 확인합니다.
