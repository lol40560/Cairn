# 기존 Cairn 코어 기능 조사

조사 기준: `afc09834c1f0ce206ab08ec042262c4955ea710c` (PR #5 병합 커밋). 아래 `경로:줄`은 모두 별도 체크아웃 `reference-cairn`의 이 커밋을 가리킨다. [고정 소스](https://github.com/lol40560/Cairn/tree/afc09834c1f0ce206ab08ec042262c4955ea710c), [참고 PR](https://github.com/lol40560/Cairn/pull/5).

실제 구현과 테스트 소스를 읽은 정적 조사다. 이 조사에서 구버전 앱·테스트를 실행하거나 기존 사용자 프로젝트와 `.cairn` 데이터를 열거나 변경하지 않았다. 아래에서 “구현됨”은 실행 경로가 존재한다는 의미이며, 이번 작업에서 런타임 통과를 재확인했다는 의미가 아니다. 새 앱의 구현·검증 상태는 별도 단계 보고서가 기준이다.

## 가장 중요한 구분

- 기존 동기화 단위는 **파일 저장 후 발생한 diff 또는 전체 파일 blob**이다. Chokidar가 파일 내용을 읽고 baseline과 비교해 operation을 만든다. Yjs 문서 identity, 문자 단위 공동 편집, 상대 커서 프로토콜은 이 코어에 없다 (`watcher/watcher.ts:131`, `watcher/watcher.ts:379`, `oplog/types.ts:11`, `sync/protocol.ts:241`).
- 기존 P2P 연결은 인증된 소켓의 존재를 확인한다. 전체 프로젝트 파일 목록·hash·기준 revision·모든 대상 클라이언트 반영을 확인하는 프로토콜 ACK는 없다. README도 이를 한계로 명시한다 (`sync/protocol.ts:241`, `README.md:127`, `README.md:169`).
- 기존 checkpoint 생성·비교·프로젝트 복원은 실제 코드가 있다. 반면 session rollback은 분석만 가능한 범위이며 안전한 자동 3-way revert 구현이 없다고 명시되어 있다. `auto-before-revert` 타입 이름만으로 rollback 구현을 추정해서는 안 된다 (`checkpoints/index.ts:10`, `checkpoints/index.ts:134`, `electron/main.ts:1110`, `README.md:170`).
- operation의 `author`와 `source`는 작성자 문자열 및 local/remote/unknown 출처다. 특정 AI가 파일을 작성했다는 검증 증거가 아니다. claim의 `kind: 'agent'` 역시 호출자가 선언하는 메타데이터다 (`oplog/types.ts:3`, `oplog/types.ts:14`, `edit-claims/index.ts:11`).
- 기존 oplog에는 이미 영속 기록, hash 중복 제거, `received/applied/rejected` 상태, 중단된 원격 작업 재시도가 있다. 따라서 “기존 앱에 영속성이나 복구가 전혀 없다”고 평가하면 부정확하다 (`oplog/oplog.ts:209`, `sync/sync.ts:609`, `sync/sync.ts:645`). 새 앱에 필요한 것은 지정 호스트의 권위 있는 CRDT 저장 및 그 저장을 증명하는 ACK다.

## 새 설계가 반드시 바꿔야 하는 경계

1. **권위 상태:** 구버전은 각 peer의 파일과 oplog를 교환한다. 새 앱은 지정 호스트의 CRDT binary 상태·파일 메타데이터가 공유 상태의 기준이다. 호스트 자신의 editor도 동일 인증·인가·operation 프로토콜을 통과한다.
2. **ACK 의미:** 연결, 서버 영속 저장, 실제 파일 반영, 연결된 팀원 적용, revision R까지 확인됨을 각각 보관·표시한다. 기존 `have`나 `snapshot-done` 이름을 durable ACK로 바꾸어 설명하는 것으로 해결되지 않는다.
3. **파일 identity:** fileId와 path를 분리하고 삭제 tombstone 및 문서 generation을 넣는다. 일반 재시작은 identity/generation을 유지하고, 과거 복원은 새 서버 작업으로 기록한다.
4. **외부 편집:** 안전한 baseline일 때만 delta를 CRDT에 반영한다. 기준을 모르는 저장 또는 경합은 버전을 보관하고 검토한다. 외부 앱의 미저장 buffer를 관측할 수 없다는 한계를 UI와 문서에 남긴다.
5. **저장과 materialization:** DB commit과 파일 쓰기를 한 원자 작업으로 주장하지 않는다. queue/intent, 임시 파일, 실제 디스크 hash 재확인, 교체 실패·재시작 복구, 외부 변경 발견 시 우선 보존을 구현한다.
6. **운영:** 구버전 `startRoom`은 Electron active project의 watcher·oplog에 직접 연결된다 (`electron/main.ts:723`). 새 서버 코어는 renderer 없는 별도 프로세스에서도 작동하고, 프로젝트당 writer/watcher 소유권을 하나로 제한해야 한다.

## 확인한 실패 경로와 확신의 범위

다음은 소스에서 분기·호출 순서를 확인한 사실이다. 이번 조사에서 고장 주입으로 재현한 결과는 아니다.

- **바이너리 충돌 보호의 공백:** 송신 op에 baseHash가 있어도 수신 적용 함수는 이를 비교하지 않고 파일을 쓴다 (`sync/sync.ts:769`–`:810`). 따라서 동시 바이너리 변경의 양쪽 버전 자동 보존이 구현됐다고 볼 수 없다.
- **큰 텍스트의 충돌 경로 우회:** full-text-blob은 UTF-8 검증 뒤 직접 전체 파일 쓰기로 이동한다 (`sync/sync.ts:814`–`:835`). 일반 텍스트 diff의 3-way 보호와 동등하지 않다.
- **쓰는 순간의 디스크 경합:** 텍스트 병합 계산과 실제 `writeFile` 사이에 디스크 hash/revision을 재확인하는 코드가 없다 (`sync/sync.ts:956`, `electron/main.ts:744`). watcher baseline 업데이트는 파일 쓰기 이후다.
- **휴지통 metadata 실패:** `TrashManager.moveToTrash`는 먼저 원본을 content로 이동하고, metadata 쓰기 등 후속 오류가 나면 catch에서 해당 entry 디렉터리를 재귀 삭제한다 (`trash/index.ts:54`–`:67`). 새 구현은 metadata 실패 때 이미 옮긴 콘텐츠를 남기거나 안전하게 원복해야 한다. 일반 watcher가 제공하는 baseline 복구가 모든 caller/경합에서 이 실패를 완전히 상쇄한다고 가정하지 않는다.
- **충돌 해결 중 새 변경:** `resolve` API는 expected revision/hash 인수가 없다 (`conflicts/index.ts:52`). 검토가 시작된 후 파일이 바뀌어도 remote/merged 적용 직전 확인 단계가 없다.
